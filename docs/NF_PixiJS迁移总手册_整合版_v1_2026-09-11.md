## Ⅰ-1 · 问题解剖：为什么「12k = 低分辨率」

粒子画的「分辨率」= 点云密度。同样一块 2K 画布下的对照：

| 点数 | 细节网格（等效） | 2K 全屏点格间距 | 观感 |
|---|---|---|---|
| 12,000（旧规格） | ~110 × 110 | ~17 px | 粗、糊、「一坨」 |
| 50,000 | ~224 × 224 | ~8.6 px | 粗油画 |
| **100,000（新基准）** | ~316 × 316 | **~6 px** | **细密油画 ✓** |
| 200,000 | ~447 × 447 | ~4.3 px | 极细，近印刷 |
| 1,000,000 | ~1000 × 1000 | ~2 px | 点感消失（过头） |

> 结论：要「顶尖」，需要 **10 万级**点数。12k 是当年为『Canvas2D 60fps 上限』服务的保守值——**方向反转：视觉定标准，技术找实现**。
> 第二层问题：物理像素纪律（backing store = CSS 尺寸 × DPR、整数尺寸、禁 CSS 缩放画布）。任何一层失守都会「糊」——两层都要治。

> **【防雷索引】** 点数档位与填充成本 → §2-D4、§4 矩阵；像素纪律 → §2-C8、Ⅰ-2 清晰度军规。

## Ⅰ-2 · 顶尖规格（新目标）

> **【防雷索引】** DPR → §2-C8；渲染管线 → §2-A7、A8、C6；数据契约 → §2-B 类全部；体积 → §2-E2；停帧 → §2-C1；清晰度验收 → §4 矩阵。

1. **渲染引擎**：**PixiJS v8**（WebGL 后端；WebGPU 实验性，生产用 WebGL）。MIT 免费。**精确锁 8.20.1**（sha256 校验见 §2-A1）。官方数据：粒子容器「100K+ 轻松」、M3 实测百万级 @60fps。
2. **点数**：基准 **100,000**；实验档 150k / 250k（bench 对照）；**终值 = 作者 PC + 作者手机双达标（60fps）下的最高档**。
3. **DPR**：**原生 ≤3×**，取消旧「≤2」上限；`?dpr=` 保留为对照实验闸门。
4. **渲染管线**：单张高分辨率白色软点贴图 + 每粒子 tint/alpha（**弃用**调色板图集 + 分桶——那是 Canvas2D 无逐精灵着色时代的复杂工程，GPU 下不需要）；`ParticleContainer`（仅 position 动态；成画期 alpha 动态，其余静态）。
5. **清晰度军规（五条）**：
   ① `canvas.width/height = CSS × DPR`，取整；
   ② CSS 尺寸取整数 px；
   ③ 禁止对画布做 CSS transform 缩放（或仅整数倍）；
   ④ 软点贴图高分辨率生成（如 128×128），禁止放大低清贴图；
   ⑤ 验收 = 2K 屏 100% 缩放「无明显糊感」+ 200% 放大查点缘 + 对照油画参考。
6. **数据契约 v3（二进制 · 高密度）**：`meta.json`（id/w/h/count/palette）+ `points.bin`（定长 5B/点：x,y = uint16 ×2，调色板索引 = uint8）。**JS 端用 DataView 直读（零结构解析；5B 步长为非对齐结构，禁 TypedArray 视图）**〔整合修订①，见 §6.3〕。体积目标 **≤200KB（br）@100k**；加载 = 首屏后预载（不阻塞 LCP），成画区进入前完成解码。源图采样 ≥2200px。
7. **保留项（照旧）**：按需渲染停帧（全静止 → 停 ticker）；凌厉运动曲线；成画 1.5s 可打断；reduced-motion 静态成画；单色纪律与全站禁止清单；软点不做像素化。
8. **bench 升级**：新增「2K 清晰度验收」与「点数档对照（100k / 150k / 250k）」；指标沿用（均值 FPS / p95 / 1% low / long task）+ 内存长跑。

## §2 · 失误全图谱（72 条）

> 使用说明：每条 = 失误形态 → 根因深析 → 完整解决方案 → 依据 / 查证 → 检索词。
> 标「点名风险①/②/③」对应用户点名的三类高发风险：① PixiJS v8 API 巨变；② 二进制字节对齐；③ 渲染/物理解耦误删。

### A 类 · 版本与 API（PixiJS v8 巨变专场）

**A1 · 版本漂移（装错版本 / 未锁定）**
- 失误形态：直接 `npm install pixi.js` 或从不可信 CDN 拉 latest——拿到与审计基线不一致的版本（v7 / v8 早期版 / 未审计新版），后续全部验证失效。
- 根因深析：v8 小版本仍在演进（当前审计基线 **8.20.1**）；包管理器与 AI 默认「取最新」或「取记忆里的 8.x」；训练数据版本号混乱。
- 完整解决方案：
  1. **锁定 8.20.1**：package.json 精确版本（无 `^` / `~`），或直接使用已审计 vendor 单文件；
  2. 拉取后必须校验三件套：sha256 = `994859…4d53`、字节 818,871、gzip -9 = 230,584——任一不符即失败拒用；
  3. 版本变更 = 变更申请（查 changelog + 重跑全量验收）；禁止「顺手升级」。
- 依据 / 查证：E0；`sha256sum vendor/pixi.min.js`
- 检索词：`PixiJS v8 changelog breaking changes 8.20` / `npm save-exact lockfile`

**A2 · await app.init() 时序失误（点名风险①家族）**
- 失误形态：写出 `const app = new Application({...}); app.stage.addChild(x);`（v7 模式）——v8 构造器不再自动初始化，直接使用得到空对象 / 报错。
- 根因深析：v8 改为**异步初始化**；`ApplicationOptions` 从构造器搬进 `init()`；训练数据里 v7 同步模式占绝对多数。
- 完整解决方案：
  1. 唯一启动模板（贴死）：`const app = new Application(); await app.init({ ... }); document.body.appendChild(app.canvas);`
  2. 所有 Pixi 使用点必须在 `init` 完成之后（顶层用 async IIFE 包裹）；
  3. 配置对象只传 `init()`，不传构造器；
  4. 冒烟验收：启动 5 秒内截图非空 + 控制台 0 报错。
- 依据 / 查证：Q1（E2 行 114–144）
- 检索词：`PixiJS v8 await app.init async initialisation ApplicationOptions`

**A3 · 包结构混用（@pixi/* 子包残留）**
- 失误形态：代码里出现 `import { Application } from '@pixi/app'` 等 v7 子包路径；或按旧教程写多包导入。
- 根因深析：v7 拆包（@pixi/app、@pixi/sprite…），v8 回到**单包**；训练数据两代混杂。
- 完整解决方案：
  1. 一律从 `'pixi.js'` 单包导入；自定义构建才用 `import 'pixi.js/<feature>'`（依官方 Custom Builds 指南）；
  2. 黑名单 grep：`@pixi/` 出现即拒收（明确使用已迁移生态包除外，需单独批准）；
  3. 加载后 console 无「Failed to resolve module」。
- 依据 / 查证：Q2（E2 行 45–63）
- 检索词：`PixiJS v8 new package structure @pixi/app single package`

**A4 · Graphics API 旧写法（点名风险①家族 · 最高频）**
- 失误形态：任何 `beginFill / drawRect / drawCircle / drawPolygon / endFill / lineStyle`……v8 已删除，直接 TypeError。
- 根因深析：v8 Graphics 重构为「**先建形状、再 fill/stroke**」链条；Line 术语改 Stroke；训练数据几乎全是 v7 样板。
- 完整解决方案：
  1. 只允许 v8 形态：`g.rect(x,y,w,h).fill(color)`；描边 `.stroke({ width, color })`；
  2. 更名对照表（Q3）贴进任务卡；画任何形状前先对照；
  3. 全库黑名单 grep：`beginFill|endFill|lineStyle|drawRect|drawCircle|drawPolygon|drawEllipse|drawRoundedRect`——每处必须替换；
  4. 连锁注意：`endFill()` 无对应物（删除，`.fill()` 即终点）。
- 依据 / 查证：Q3（E2 行 184–232）
- 检索词：`PixiJS v8 Graphics rect fill stroke migration drawRect removed`

**A5 · Texture 体系旧概念**
- 失误形态：写 `new BaseTexture(...)` / `texture.baseTexture` / 期待纹理自动按 URL 加载。
- 根因深析：v8 删除 BaseTexture；**纹理不再管理加载**（职责上移到 Assets / 开发者）；来源家族换血。
- 完整解决方案：
  1. 加载用 `Assets.load()` / `Assets.add({ alias, src })`（注意签名对象化）；
  2. 全库 grep：`BaseTexture`、`.baseTexture`——出现即查 Q4 再改；
  3. 五源记忆：TextureSource / ImageSource / CanvasSource / VideoSource / BufferSource（软点贴图 = ImageSource）。
- 依据 / 查证：Q4（E2 行 146–183）
- 检索词：`PixiJS v8 BaseTexture removed TextureSource assets load`

**A6 · app.view / 旧属性名**
- 失误形态：`document.body.appendChild(app.view)`；`new Application({ view })`；resize 逻辑引用 `app.view.width`。
- 根因深析：v8 属性更名 `Application.canvas`；选项搬家（见 A2）。
- 完整解决方案：
  1. 挂载一律 `app.canvas`；canvas 相关配置进 `app.init({...})`；
  2. 全库 grep：`app.view`——逐处核对；
  3. resize / DPR 接线统一走 C8 接线表。
- 依据 / 查证：Q5（E2 行 743–757）
- 检索词：`PixiJS v8 Application view canvas replaced`

**A7 · ParticleContainer 语义变更（点名风险①家族）**
- 失误形态：把 `Sprite` 塞进 PC（v7 做法）；或期待 PC 支持 children / filters / masks。
- 根因深析：v8 PC 重写——**不再处理 Sprite，改用轻量 `Particle`**；不支持高级功能；粒子必须共享同一纹理源。
- 完整解决方案：
  1. 粒子 = `new Particle({ texture, x, y })` + `container.addParticle(particle)`；禁用 addChild；
  2. 设计确认：点云不需要 filters / masks / children（本项目 = 软点贴图 + tint，满足）；
  3. 纹理源统一：全部粒子同图（单张软点贴图 → 天然满足；禁止中途混图）。
- 依据 / 查证：Q6（E13）/ Q7（E7）
- 检索词：`PixiJS v8 ParticleContainer Particle addParticle sprites removed`

**A8 · PC 静态 / 动态属性误配（渲染不刷新 / 性能塌方）**
- 失误形态：改了粒子 color / scale 但屏上不动（静态属性只上传一次）；或全部设 dynamic 导致每帧全量上传、帧率暴跌。
- 根因深析：v8 静态/动态属性系统：静态 = 首传后不动、动态 = 每帧重传；**默认仅 position 动态**；静态变更需手动 `update()`。
- 完整解决方案：
  1. 属性规划（本项目）：position 动态（物理每帧写）+ alpha 动态（成画期，依编一 Ⅰ-2）；tint / scale / rotation 静态（除非视觉需要）；
  2. 任何静态属性批改后必须 `container.update()`；
  3. bench 记录 dynamic 集合版本（性能回归对比用）。
- 依据 / 查证：Q6 / Q7
- 检索词：`PixiJS v8 ParticleContainer static dynamic properties update method`

**A9 · PC boundsArea 缺省（剔除 / 命中问题）**

  1. 设 `container.boundsArea = new Rectangle(0, 0, W, H)`（覆盖点云活动域）；

### B 类 · 二进制数据契约（点名风险② · 字节对齐专场）

> 契约基准：数据契约 v3 = `points.bin`，**5 字节/点**（x,y = uint16 + idx = uint8；字段顺序以编一 Ⅰ-2 数据契约原文为准，本手册统一按 x,y,idx 演示）。

**B1 · 字节序未显式声明（点名风险② · 根因）**
- 失误形态：Python 端 `struct.pack('HHB', ...)`（默认 native，平台相关）；JS 端 `new Uint16Array(buffer)` 直接读——在大端环境或读法不匹配时点云全乱。
- 根因深析：native 默认 = 平台字节序（+可能的 pad）；TypedArray 永远用平台字节序、**无法指定**；双方各自「隐式假设小端」= 定时炸弹。
- 完整解决方案：
  1. 契约声明写死：**全链路 little-endian（小端），双端强制显式**；
  2. Python：`struct.pack('<HHB', x, y, idx)`，或 numpy `dtype='<u2,<u2,<u1'`；
  3. JS：`DataView.getUint16(off, true)`——第二参数 `true` 必传；
  4. 禁止依赖「本机恰好是小端」的巧合。
- 依据 / 查证：Q8 / Q9 / Q10
- 检索词：`struct pack little endian explicit cross-platform` / `DataView getUint16 littleEndian true`

**B2 · struct 默认对齐 pad 字节（点名风险② · 元凶）**
- 失误形态：`struct.calcsize('@HHB')` = 6（含 pad）≠ 5；文件按 6B/点写入，JS 按 5B/点读 → **从第 2 点起全部错位**。
- 根因深析：native 模式按 C 编译器规则插入对齐 pad；「代码看起来对，字节悄悄多一个」。
- 完整解决方案：
  1. 外部交换格式**禁用裸格式串**；必须带前缀 `<`（本项目）或 `=`；
  2. 黄金断言进生成脚本：`assert struct.calcsize('<HHB') == 5`；
  3. 回读自检用 `struct.iter_unpack('<HHB', data)`。
- 依据 / 查证：Q8（E3 pad 警告原文）
- 检索词：`struct calcsize native pad bytes alignment`

**B3 · 字段顺序 / 语义错位**
- 失误形态：两端对 (x,y,idx) 顺序理解不一 → x/y 互串、idx 错位（颜色全乱）；或坐标系约定不一（y 轴方向）。
- 根因深析：无单一事实来源的契约表；口头约定易漂移。
- 完整解决方案：
  1. 契约表冻结（写进两端注释）：`offset 0 = x(u16) / 2 = y(u16) / 4 = idx(u8)`，总长 5B；
  2. 坐标系声明一处定义、两端遵守（y 轴方向写进契约）；
  3. 记忆点：`<` 后顺序 =「先 x 后 y 再 idx」。
- 依据 / 查证：契约 v3 原文 + §4 矩阵
- 检索词：`binary layout contract point cloud x y index stride 5 bytes`

**B4 · 步长 / 偏移数学错误**
- 失误形态：`off = i*6`（把 5 写成 6）；`i*5+4` 该读 idx 却读 y 低字节；最后一点越界读。
- 根因深析：手写魔法数字；无断言、无边界测试。
- 完整解决方案：
  1. 常量表：`STRIDE=5, OFF_X=0, OFF_Y=2, OFF_IDX=4`；禁止散落魔法数；
  2. 全量断言：`expected = count*STRIDE; if (buf.byteLength !== expected) throw`；
  3. 单测：count=1 边界样本 + 末点样本。
- 依据 / 查证：—
- 检索词：`DataView byte offset stride reading buffer assert byteLength`

**B5 · TypedArray 非对齐访问抛错**
- 失误形态：`new Uint16Array(buffer, 1, n)`（offset 非 2 的倍数）直接 RangeError；或对 5B 步长数据整段 TypedArray 视图扫描。
- 根因深析：TypedArray 视图对齐约束（Q9）；**5B/点本身非 2 的倍数，永远无法直接视图化**。
- 完整解决方案：
  1. 禁用 TypedArray 直接视图读 points.bin；统一 **DataView**（允许非对齐偏移）；
  2. 若未来要 TypedArray 加速：先用 DataView 拷贝到对齐缓冲，再视图化；
  3. grep 防线：数据读取模块出现 `new (Uint16|Float32|Uint32)Array(` → 复核。
- 依据 / 查证：Q9（E4 对齐条）
- 检索词：`TypedArray byteOffset must be aligned BYTES_PER_ELEMENT RangeError`
- 整合注：源稿「TypedArray 视图」表述已按整合修订①统一为 DataView 直读（见 §6.3）

**B6 · DataView 默认大端陷阱**
- 失误形态：`view.getUint16(off)`（忘传 `true`）→ 高低字节颠倒，数值全错（如 0x03FF 读成 0xFF03）。
- 根因深析：DataView 默认 big-endian（Q10）——与「多数平台小端」直觉相反。
- 完整解决方案：
  1. 封装读取器：`const u16 = (o) => view.getUint16(o, true)`——所有读取必经此函数；
  2. review 检查项：搜 `getUint16(` 后必须跟 `, true`；
  3. 双端校验用 1023 样本对照（见 B10）。
- 依据 / 查证：Q10（E5）
- 检索词：`DataView big endian default littleEndian parameter`

**B7 · 数值范围与量化一致性**
- 失误形态：x 超 65535 被静默截断（wrap）→ 点位跳错；idx 超 255 溢出；浮点取整两端策略不一（floor vs round）→ 半像素漂移。
- 根因深析：无量化协议；JS / Python 取整与舍入默认行为不同。
- 完整解决方案：
  1. 写入前断言 / clamp：`0<=v<=65535`，越界**抛错不静默**；idx ∈ [0, paletteN]；
  2. 量化规则统一：双端一律 `floor(v + 0.5)`（规避 Python 银行家舍入差异）；
  3. 采样阶段保证坐标域映射铺满 [0,65535]。
- 依据 / 查证：—（工程规约）
- 检索词：`uint16 clamp quantize round consistency javascript python`

**B8 · 生成端隐藏不一致（Python 侧）**
- 失误形态：用 `array.array` / pandas / 默认 `tobytes()`（平台相关）；经 JSON 中转损失精度；numpy 未指定 dtype 字节序。
- 根因深析：Python 生态「默认 native」太多；只在小端机上开发测不出来。
- 完整解决方案：
  1. 只允许两种写出路径：`struct.pack('<...')` 循环，或 numpy 显式 `'<u2' / '<u1'` dtype 的 `tobytes(order='C')`；
  2. 禁止 array.array / pickle / JSON 中转二进制；
  3. 生成脚本内置：`sys.byteorder` 打印 + `calcsize` 断言 + 输出 sha256。
- 依据 / 查证：Q8
- 检索词：`numpy dtype little endian tobytes explicit struct pack export`

**B9 · 传输与完整性**
- 失误形态：fetch 没用 `arrayBuffer()`（text 模式损坏字节）；服务器 charset 转换；文件被截断 / 拼接错。
- 根因深析：二进制资源管道常见坑；无完整性校验。
- 完整解决方案：
  1. `const buf = await (await fetch(url)).arrayBuffer();`；

- 依据 / 查证：—
- 检索词：`fetch arrayBuffer binary content-length verify sha256`

**B10 · Round-trip 黄金测试（总闸门）**
- 失误形态：双方各自「看都对」，合起来才暴露，难以定位。

### C 类 · 架构迁移与解耦（点名风险③ · 渲染/物理分离专场）

**C1 · 双循环冲突（物理循环 vs Pixi ticker）——点名风险③核心**
- 失误形态：既保留自建 rAF 物理循环、又启动 Pixi ticker → 双时钟、相位漂移、抖动；或删了旧循环却忘搬家。
- 根因深析：迁移时「渲染循环归属」未定义；两个 rAF 各自计时，物理与渲染不再同帧。
- 完整解决方案（单时钟纪律）：
  1. 唯一时钟 = Pixi `app.ticker`；物理步进挂**高优先级**（官方示例 Q13：`UPDATE_PRIORITY.HIGH`），保证物理先于渲染、同帧执行；
  2. 禁止任何第二个 rAF / setInterval 驱动渲染或物理；旧循环删除前必须完成搬家 + 验收；
  3. 时基规范：模拟步进用 `ticker.deltaTime`（或固定步长累加器），全站同源。
- 依据 / 查证：Q12 / Q13
- 检索词：`PixiJS ticker physics update UPDATE_PRIORITY single loop`

**C2 · 旧 rAF 内 ctx 依赖代码被「顺手删」（点名风险③原话）**
- 失误形态：迁移时把原 rAF 回调里「看起来是旧渲染」的整段删掉——里面混着物理更新、状态写回、事件接线 → **物理停摆 / 画面静止 / 交互失效**。
- 根因深析：把「渲染出口替换」误当「循环整体重写」；删除前无引用分析。
- 完整解决方案：
  1. **结构性隔离先行**：把 rAF 回调拆为「物理步进 `step(dt)` / 状态快照 `snapshot()` / 绘制出口 `renderFrame()`」，迁移只替换 renderFrame 内部实现；
  2. 删除白名单制：仅标 `// == RENDERER-SWAP ==` 的段落允许改动；step / snapshot 区段设物理防火墙（禁删）；
  3. 每处删除行必须给出「替代位置」说明，否则拒收；
  4. 验收锚点：物理黄金样本（固定输入 × 1000 步 → 位置序列 sha256 一致）。
- 依据 / 查证：Q12（物理属于 ticker 用户逻辑层）
- 检索词：`separate physics from renderer loop refactor requestAnimationFrame canvas`

**C3 · 中间态不可运行（半迁移白屏）**
- 失误形态：一次性大改，出现「渲染已换、物理没接」的中间态，无法定位问题。
- 根因深析：大爆炸式迁移；无小步验证。
- 完整解决方案：
  1. 五步小步走（H1）：依赖落位 → Hello 冒烟 → 数据桥 → 点云上线 → 物理联调；每步可运行、可截图；

**C4 · 输入 / 事件坐标桥断裂**
- 失误形态：拖拽时坐标跳变（client 坐标直接当 stage 坐标）；canvas 替换后旧事件接线失效。
- 根因深析：坐标链路未定义：client → canvas → stage（含 resolution / DPR 缩放）。

### G 类 · Cursor 行为模式（元风险 · 12 条）

> 本类不针对代码，而针对 AI 编码代理的**行为倾向**。每条给出「识别信号 + 反制手段」。

**G1 · 凭记忆写 API（幻觉）**
- 失误形态：不查文档直接输出「看起来对」的接口 / 参数 / 选项名；编译或运行才暴露。
- 根因深析：语言模型以概率生成 API 表面；v7 语料占优（点名风险①的行为面）。
- 完整解决方案：
  1. 强制「先查后写」（§0.1 / A12）；任务卡附官方页；
  2. 提交前语法检查 + 加载冒烟（0 报错门槛）；
  3. 抽查：随机挑 3 个调用点对官方 API 页复核。
- 识别信号：代码里出现文档中搜不到的参数名。
- 检索词：`PixiJS v8 api reference verify method exists`

**G2 · 静默降级 / 偷简化**
- 失误形态：偷偷减少粒子数、跳过高 DPR、关闭 antialias、把动画改成静态图——「为了性能」。
- 根因深析：AI 倾向让代码「跑得动」，会自行妥协目标；违宪（100% 极致效果）。
- 完整解决方案：
  1. 违宪清单贴进每个任务卡（§0.2）；
  2. 参数审计：迁移前后同参数 grep 对照表；
  3. 截图对比为证——视觉不得回退；
  4. 发现即回滚 + 记 §6。
- 识别信号：diff 里出现没人要求过的参数变化。
- 检索词：`no silent degradation policy review diff`

**G3 · 「顺手删」无关代码（点名风险③行为面）**
- 失误形态：删除「看起来没用」的代码——实际是物理核心 / 事件接线 / 状态写回。
- 根因深析：AI 以「整洁」为目标做未授权清理；静态分析能力有限，误判引用。
- 完整解决方案：
  1. 删除白名单制（C2）；
  2. 每处删除行必须注明「替代位置」，否则拒收；
  3. 物理黄金样本对照（C2 验收锚点）。
- 识别信号：diff 出现无说明的删除行。
- 检索词：`code deletion policy reference check physics`

**G4 · 越界修改（scope creep）**
- 失误形态：改 A 功能时顺手重构 B、C、D；变更范围失控。
- 根因深析：AI 的「帮助性」驱动；无范围约束。
- 完整解决方案：
  1. 任务卡写明「允许修改文件清单」；清单外改动一律退回；
  2. diff 审查逐文件核对；
  3. 额外改进写「建议区」（只记录不执行）。
- 识别信号：diff 触及任务卡外路径。
- 检索词：`scope lock allowed files review`

**G5 · 整文件重写覆盖（丢细节）**
- 失误形态：不 diff 而整文件重写，丢掉注释、微妙逻辑、历史修复。
- 根因深析：重写比打补丁「省事」；AI 偏好完整输出。
- 完整解决方案：
  1. **只允许 patch 式小步 diff**；整文件重写需单独申请 + 逐段对照说明；
  2. 重写后跑全量回归（§4）；

- 识别信号：diff 显示 +300/-280 式对称大块。
- 检索词：`surgical edit patch not rewrite review`

**G6 · 假完成报告**
- 失误形态：声称「已完成 / 已修复」但无证据；实际未运行、未验证。

**G7 · 上下文丢失 / 长任务漂移**

## §3 · 死命令清单（Cursor 粘贴版）

> 用法：每次任务卡开头原样粘贴。任何一条与「完成」冲突时，以本清单为准。

1. 你正在迁移 NFWeb 至 **PixiJS v8.20.1**。任何 Pixi API 使用前，先查 §1 引文库或官方 `.md` 文档；**禁止凭记忆写代码**。
2. 版本锁定 `pixi.js@8.20.1`；vendor 文件 sha256 必须等于 `994859…4d53`（818,871B / gzip 230,584B）；不符即停工。
3. 启动唯一模板：`const app = new Application(); await app.init({...}); document.body.appendChild(app.canvas);`——任何 app 使用不得早于 `init` 完成。
4. 只从 `'pixi.js'` 单包导入；出现 `@pixi/` 即违规。
5. Graphics 只允许新形态：`rect().fill()` / `.stroke({...})`；任何 `drawXxx / beginFill / endFill / lineStyle` 即违规。
6. ParticleContainer 只加 `Particle`（`addParticle`）；所有粒子共享同一纹理源；静态属性修改后必须 `update()`；bounds 自设 `boundsArea`。
7. 全站唯一时钟 = `app.ticker`；**禁止**第二个 rAF / setInterval；物理挂高优先级（`UPDATE_PRIORITY.HIGH`）。
8. 物理核心区与 ctx 依赖区**禁止删除**（白名单制）；每处删除行必须注明「替代位置」，否则整个提交拒收。
9. `points.bin` 契约：`<HHB` 小端无填充、5B/点；JS 读取 `DataView ... getUint16(o, true)`——`true` 必传；读写前后断言 `stride=5` 与总长。
10. 禁止新增任何依赖 / 构建工具；禁止改加载方式；禁止版本变更；禁止静默改动任何视觉参数。
11. 每次交付附证据包：命令 + 原始输出 + 截图 + 哈希；缺一 = 未完成。
12. 有疑问先停下提问；不许自行决定设计（视觉参数 / 交互语义 / 文案属不可自行决定项）。
13. 每步单一目标、可运行、可回滚；失败回退上一步，禁止叠加修复。
